# Changelog

## 0.1.3 - 2026-09-26

- Popup: **Passing checks** lists the checks that passed, not only their number ("29 passing checks" under the score is now followed by the checks themselves). Each check is shown as Sitelemetry reported it, in the report language: its title and, in smaller text, its evidence. The checks are grouped by security module with the module names of sitelemetry.com, in the order sitelemetry.com lists the modules, each group heading with its number of checks; a check whose id belongs to no known module goes under "Other checks", last. Only checks with status `ok` are listed; skipped, unavailable and other checks are not. The data is the `auditDetails.checks.items` list Sitelemetry already returns with every `audit_security` result (the general `/mcp` endpoint sends the complete list), so nothing new is requested or sent.
- The result stored on the device keeps up to 300 passing checks with only what the popup shows (id, title up to 180 characters, evidence up to 300; the location the service also sends is not kept) and at most 40,000 characters of that text, so a large audit keeps the stored result small. When the service counted more passing checks than were kept, the heading gives both numbers ("Passing checks (300 of 342)"), so it agrees with the count under the score, and a note at the top of the section says how many were counted but not kept. A result stored by 0.1.2 has only the count: the section shows it and says that the list appears after the next audit of the site. No note refers to a report in the Sitelemetry app: the service keeps none for audits run through the general `/mcp` endpoint.
- Popup: **Passing checks** and **What was not measured** are collapsible sections, closed by default, placed after the findings in that order. Each heading shows the number of items (for example "Passing checks (29)", "What was not measured (7)", "合格したチェック（29件）" and "測定されなかった項目（7件）" in Japanese) after an arrow that points right while the section is closed and down while it is open; clicking the heading, or Enter or Space on it, opens the section. They are native `<details>`/`<summary>` elements, so keyboard and screen-reader support come from the browser and no script is added to the markup. The arrow has empty alternative text, so a screen reader announces the heading and its expanded or collapsed state without the arrow glyph (the arrows of the findings are silenced the same way), and the content of both sections is indented to line up with the heading text. The headings keep the look of the other section headings in light and dark mode, long evidence wraps within the popup width, and the arrow turns without animation when reduced motion is requested. Both sections are closed again for every new result and the state is not stored; while the same result is shown again (a storage update, or the plan facts arriving after the popup opened) an open section stays open and keyboard focus stays on its heading.
- Popup, findings: no text points to a report in the Sitelemetry app any more. Sitelemetry saves no report of an audit run through the general `/mcp` endpoint the extension uses (the job keeps its result only while it is polled), so "N more finding(s) are listed in the full report in the app" was wrong. The popup still lists up to ten findings, most severe first; under them, one note says how many more findings of the stored result the list does not show and, when the AI fix prompt includes all of them, says so ("4 more finding(s) of this result are not shown in this list; the AI fix prompt includes them."), and another says how many findings Sitelemetry counted but did not include in the result ("Sitelemetry counted 6 more finding(s) that are not included in this result."). A result whose findings were counted but none sent shows that note instead of "No findings were reported for the measured checks.". "What was not measured" without details says that the result does not say which measurements were unavailable, instead of that the full result in the app lists them. The job errors for the time budget and a failed connection offer Check again without "or open the app", and an audit the browser interrupted before Sitelemetry confirmed a job says that it may still have run and used a security scan, instead of sending the user to the audits of the account in the app. The report link is still shown only when the service sends one.
- New translated messages in all ten locale folders: the section heading pattern with the number of items (`sectionCount`, with a no-break space before the parenthesis and full-width parentheses in Japanese and Chinese) and with the number listed of the number counted (`sectionCountOfTotal`), the "Passing checks" title in the wording of sitelemetry.com, "Other checks", the notes for checks counted but not kept, a result sent without the list and a result stored by 0.1.2, and the findings notes (`moreFindingsNotShown`, `findingsNotIncluded`, `findingsNoneIncluded`). `moreFindings`, `nmUnknown`, `errorTimeoutJob`, `errorTransportJob` and `errorInterrupted` are reworded in every locale, in neutral wording, and their descriptions tell translators not to refer to a report elsewhere.
- Copy AI fix prompt: its notes no longer point to "the full report in the Sitelemetry app". Findings Sitelemetry counted but did not include in the result are named as not included ("Note: this result includes 4 of the 11 findings Sitelemetry counted for this audit. The other 7 findings were not included in it, so they are not listed here."); when none was sent, the assistant is asked not to guess them or give generic advice in their place, and no longer to start by asking the user to paste them, since the user has no other copy: it says that their details are missing from the result and suggests running the Sitelemetry audit of the site again, and gives the per-finding steps only for findings the user then pastes. The least severe findings left out to stay within 30,000 characters are named as not included in the prompt, with a new audit after the fixes listing those that remain. "Not measured" entries beyond the section's budget are counted as left out to keep the prompt short, and the prompt says that the extension popup lists all of them. The injection safeguards, the budgets and the 30,000-character cap are unchanged, and the prompt still carries only the number of passing checks. `composeFixPrompt` returns the prompt with the number of stored findings it lists, which the popup uses for its note.
- Developer harness: the `completed` and `redirects` scenarios return realistic check lists (passing checks across several modules and, for `redirects`, skipped checks, in English and Turkish), a `legacy` scenario shows a result stored by 0.1.2, and a `many` scenario shows the findings notes (14 findings sent of 20 counted).
- Store assets: listing screenshot 2 (`store-assets/screenshot-2.png`) is taken again from the 0.1.3 build, since the old one showed the removed note "4 more finding(s) are listed in the full report in the app." It shows the whole popup of the same stored partial result of https://sitelemetry.com in two panels side by side, with the new findings note, "Passing checks (64)" closed and "What was not measured (3)" open. STORE-LISTING.md and SUBMISSION.md say to replace it in both stores.
- Tests: the popup's result view is rendered in Node by the real popup module (a small DOM in `test/fake-dom.mjs`, no dependency) to check both closed sections, their headings and counts in several languages, the groups and checks, the order of the sections, a 0.1.2 result, a list cut short (both numbers in the heading, the note first) and the open state and focus across re-renders, and checks in the stylesheet that the arrows have empty alternative text and that the content of a section lines up with its heading text; `test/passing.test.mjs` covers which checks are kept (without their location), the clipping and the limits, the module of each check id, the notes (none refers to a report in the app) and the unchanged AI fix prompt. `test/report-words.mjs` holds the words for "report" and "app" in each language: `test/i18n.test.mjs` checks that no message pairs them, that only the messages about the account, the verification, the terms and the API key name the app and only the report link label, the report language and "reported" name a report, that the notes and job errors name neither, and that the findings notes read as facts, not failures; `test/fix-prompt.test.mjs` checks every note of the prompt, and the prompt's own sentences in its source, the same way, and the number of findings `composeFixPrompt` lists; `test/popup.test.mjs` renders the findings notes (in English, Turkish and Japanese, for findings beyond the list, findings not sent, none sent and a prompt that cannot hold them all) and checks that the report link appears only with a link from the service.
- No new permission, host permission, dependency or remote code; the content security policy is unchanged.

## 0.1.2 - 2026-09-25

- The popup and the settings page are translated into all nine Sitelemetry languages: English, Turkish, Spanish, German, French, Portuguese, Italian, Japanese and Simplified Chinese (`_locales/en`, `tr`, `es`, `de`, `fr`, `pt_BR`, `pt_PT`, `it`, `ja`, `zh_CN`; Portuguese is one translation, shipped for both Chrome locales). Chrome picks the translation from the browser's UI language; any other language, including Traditional Chinese, keeps English. Module names and the audit, scan, allowance and verification wording follow sitelemetry.com. The page's `lang` attribute follows the translation shown.
- Results in the user's language: the call that starts the audit now sends `lang` (one of `en`, `tr`, `es`, `de`, `fr`, `pt`, `it`, `ja`, `zh`, the language the popup is shown in) through the existing `audit_security` argument, so findings, reasons and messages from Sitelemetry arrive in that language. Polls still re-send the service's `pollArguments` exactly as returned; the service keeps the language of the job for its result. The language is stored with the job and the result. A job stored by 0.1.1 resumes unchanged, without a language.
- "What was not measured" names each security module as sitelemetry.com does (for example "Sensitive file exposure" instead of `exposure`) with "not measured" or "partly measured", and explains the reason when it is recognised from the module and the language-independent parts of the service's reason (HTTP status codes and counts), whatever language the service answered in: paths the site redirects (HTTP 3xx, for example to its sign-in page), rate-limits (429), answers with a server error (5xx) or leaves unanswered; ports that a firewall silently drops; scripts beyond the per-audit scan limit. The service's own reason stays visible under each explanation in smaller text (shortened to 300 characters, as before), and anything not recognised is shown as the status word and that reason. The extension now keeps up to 2,000 characters of a module's reasons, so an explanation that depends on the end of a long reason is still found (for example the scripts left outside the scan after a list of script chunks a firewall refused). When at least one item is explained, the note under the heading says that explained items come from how the site responded or from a deliberate scan limit, not from an error in the audit; otherwise it only says, as before, that unmeasured checks are not counted as passes. Long reasons wrap inside the popup instead of widening it.
- Severity count chips use a translated pattern, so a language whose adjective would have to agree with the number shows the label first (for example "crítico: 3").
- Copy AI fix prompt: the "Not measured" lines carry the same explanations and the reported reason, the prompt says that unmeasured checks have no conclusive result (the reason is listed for each) instead of that they did not run, and the assistant is asked to respond in the user's UI language instead of always English; the rest of the prompt stays English. The "Not measured" section has its own 6,000-character budget, so it never crowds out the findings. The injection safeguards and the 30,000-character cap are unchanged.
- `npm run check` also validates every `_locales` folder name against Chrome's supported locales and the translated store name and description lengths.
- Developer harness: `&lang=` picks the browser UI language (for example `tr`, `pt-BR`, `zh-CN`) and a `redirects` scenario shows a site that redirects unknown paths to its sign-in page behind a firewall.
- No new permission, host permission, dependency or remote code; the content security policy is unchanged.

## 0.1.1 - 2026-09-25

- Popup: **Copy AI fix prompt** on a completed or partial result. The extension builds a plain-text prompt from the stored result on the device (site origin, audit date, score and grade, coverage, severity counts, passing checks, every stored finding with severity, title, location, evidence, impact and the suggested fix, most severe first, the "not measured" entries and the task for the assistant) and copies it to the clipboard. The same text can be opened in a read-only field and copied by hand when the clipboard is unavailable. Finding text is marked as data and neutralized: line breaks, delimiter lookalikes and invisible characters (zero-width, bidi, Unicode Tag characters, variation selectors) are removed, so it cannot imitate the prompt's delimiters or task section or carry hidden text. The prompt never contains the API key, job ids, poll arguments or service links, and stays within 30,000 characters: long fields are shortened first, and for a very large result the least severe findings are left out with a note that says how many and that the full report in the Sitelemetry app lists them. A result whose findings were not stored asks the assistant to request them rather than giving generic advice; a partial result without findings is not described as issue-free. No new permission and no network request.
- Running view: the phase line is always the extension's own text ("Starting the audit…", "The audit is running on Sitelemetry. Results appear here automatically.", or the busy-account note). The service's running answer, which is written for MCP clients, is no longer stored with the job or shown.
- HTTP 403 is reported as "Sitelemetry refused this request (HTTP 403)." with the service's own message, if its JSON error body has one, under "Message from Sitelemetry"; only HTTP 401 is described as a rejected API key. The settings page **Test connection** makes the same distinction. A 403 result stored by 0.1.0 is shown with the new wording, and a non-JSON body (for example a proxy page) answering 401 is no longer shown as a message from Sitelemetry.
- Running view: resuming a stalled job with **Check again** no longer shows the busy-account note left over from the earlier attempt.
- Popup: copying the prompt updates the status line in place, so keyboard focus stays on the button and screen readers announce the result; storage updates for other sites no longer rebuild the result view.
- Developer harness: a `forbidden` scenario.

## 0.1.0 - 2026-09-21

Initial release.

- Manifest V3 extension for Chrome and Microsoft Edge (one package): popup, options page, module service worker; no bundler, no dependencies, no remote code, no analytics, no content scripts.
- Options page: Sitelemetry MCP API key in `chrome.storage.local` (masked field, show/hide, remove), base URL override for staging, **Test connection** (MCP `initialize` on `{base}/mcp`), ownership acknowledgement reset, privacy summary.
- Popup: **Audit this site** for the active tab origin (`activeTab`), ownership and authorization notice with a persisted acknowledgement, security audit through the MCP contract (`audit_security`), polling with the server's `pollArguments` and `retryAfterMs`, job state persisted per origin and resumed by `chrome.alarms` when the worker is suspended, result view with score, grade, severity counts, top findings with fixes, "What was not measured", report link, verification step, and the neutral plan and usage box (`utm_source=browser-extension&utm_medium=extension`). "Sign up free" link for users without a key. A job that outlives the time budget, or whose connection fails after Sitelemetry confirmed it, is kept with its `jobId` and `pollArguments` and offered as **Check again**, which retrieves the same audit instead of using a second scan; a job whose start call was interrupted before the service confirmed it is never re-sent.
- Toolbar badge with the last score for the audited site in that tab; a finished audit badges the tab only while it still shows the audited origin.
- Strict CSP (`default-src 'none'; script-src 'self'; object-src 'none'` and friends), permissions `activeTab`, `storage`, `alarms`, host permission `https://sitelemetry.com/*` only.
- Icons 16/32/48/128 rendered by a dependency-free PNG writer (`scripts/make-icons.mjs`).
- Every user-facing string in `_locales/en/messages.json` (chrome.i18n with a Node fallback).
- Tests: node:test suite against the mock server copied from the Audit Action (client, polling, outcome classification, plan box, i18n coverage), manifest validation, no-remote-code scan, PNG validation.
- Docs: README, STORE-LISTING, PRIVACY, SUBMISSION, PACKAGING; PowerShell packaging script.
